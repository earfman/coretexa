01 the problem

Agent-authored pull requests look safe. That's the danger.

Tests pass, the diff is tidy, the commit message is confident — and the research shows those PRs carry more hidden defects per change than human-written code. GitHub's own guidance is to verify them by hand, per PR: require a test that would've caught the claimed bug, trace the boundary conditions, check that CI wasn't quietly weakened. That manual chore doesn't scale past a dozen agent PRs before lunch. Coretexa automates exactly that chore.

02 how it works
VERIFIER A

Reproduce & confirm

Rebuilds the behavior the PR claims, in a fresh checkout, and runs the suite. Does it actually do what it says?

VERIFIER B

Refute by default

An independent verifier whose only job is to break it — to find the concrete input that fails. "I couldn't find a problem" is a failure to search, not a pass.

VERDICT

With a receipt

CLEARED — survived the refute pass. Or REFUTED — with the exact input/state that produces the wrong output or crash.

SAFE

Non-blocking by default

Posts as a status check + comment. It never wedges your merge queue. Turn on blocking when you trust it.

03 a real catch

Live, open, Copilot-authored PR. The gate ran straight — no cherry-picking the verdict.

REFUTED · reproduced SollanSystems/loop-engineer #80 “Prevent EventStore reads from creating -wal/-shm sidecars”

The fix works on a clean store. But when a crash leaves an events.db-wal, the read path falls back to mode=ro and SQLite creates a -shm sidecar anyway — the exact thing the PR promises to prevent. Its own new test only covers the clean branch, so it passes green while the real case leaks. Two automated reviewers (Codex + Copilot) looked at this PR and missed it.

# crash-left state on disk: events.db + events.db-wal  (no -shm)
query chosen: ?mode=ro
files before read: ['events.db', 'events.db-wal']
files after  read: ['events.db', 'events.db-shm', 'events.db-wal']   ← -shm created by a READ
RESULT: -shm sidecar created by a read? True

04 why it's different

Every other AI reviewer

  • Generates comments, summaries, suggestions
  • “Consider edge cases” — no failing input
  • Often the same vendor that wrote the PR, grading its own homework
  • Adds to the review queue it was meant to clear

Coretexa

  • Reproduces the bug with a concrete input, or refutes the fix
  • A filesystem / stack-trace receipt, not an opinion
  • Independent adversary — its incentive is to break the PR
  • Clears the good ones so reviewers only see what matters
